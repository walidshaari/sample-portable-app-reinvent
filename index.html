01 · The problem

Every shortcut becomes a change tax.

In the starting app, a business action knows a DynamoDB table name and raises a FastAPI exception. Moving storage or changing the HTTP edge means touching the action itself.

src_python/monolith/monolith.py · lines 62-73 · comments omittedstarting point
def save_user(data: dict):
    save_to_dynamodb("Users", data)
    return data

def get_user(user_id: str):
    user = get_from_dynamodb("Users", {"id": user_id})
    if not user:
        raise HTTPException(status_code=404, detail="User not found")
    return user

The problem grows with agent-generated changes: a plausible local edit can spread a platform choice through many files. A readable boundary gives a human reviewer and an assistant a smaller place to look.

When to skip the pattern: A short-lived prototype with one owner may not need these extra files. Start with one port when an action must survive a change in storage, entry point, or team.

02 · The design

Make the dependency direction visible.

A use case holds the business action, and a port names the behavior it needs. An adapter calls an external system; the composition root connects that adapter at startup. The database call stays outside the use case.

Follow the arrows in the figure: which part owns the database choice?

base_python/clean/application/use_cases/create_user.py · lines 7-22 · docstrings omittedstable action
class CreateUserUseCase:
    def __init__(self, user_repository: UserRepository):
        self._user_repository = user_repository

    async def execute(self, input_data: Dict[str, Any]) -> User:
        name = input_data.get("name")
        email = input_data.get("email")
        user_id = str(uuid.uuid4())
        user = User(user_id, name, email)
        await self._user_repository.create(user)
        return user

The port promises create, find_by_id, find_all, and delete. The registry in infrastructure/composition.py selects memory, dynamodb, or postgres from configuration. This is an explicit extension point, not a promise that every future data model will fit it.

The entity also checks input types before using string operations. A missing email or numeric name raises ValueError; the HTTP edge translates that error to 400. Entity and HTTP tests cover both outcomes in the public source. The 28 September capture from the rehearsal build shows HTTP 400 for both requests on EKS and kind. A CLI command or queue consumer can use the same entity rule without importing FastAPI.

The paired digest lines answer whether the pods match. The diagram answers what differs around them.

kind and EKS are both Kubernetes. This is placement portability within one compute model. A Lambda integration would need its own packaging and runtime proof; the EKS/kind image digest cannot establish that claim.

The published source has the same core and PostgreSQL adapter bytes as the rehearsal checkout. It uses a smaller package, so its image digest must be established with a new build and deployment before repeating the live equality claim.

Placement is an architectural option. Resilience and residency become credible only when data, traffic, recovery, access, and evidence are designed for that option.

04 · What changes

Separate a configuration flip from a technology change.

ChangeCode that movesWhat still needs work
Same PostgreSQL API, different placementDeployment settings and credentials; existing adapter remainsNetwork, secrets, operations, data movement
DynamoDB model → PostgreSQL modelNew adapter and one registry entry; core remainsBehavioral contract, schema, migration, cutover

Two adapter decisions preserve the existing behavior:

  • create() uses INSERT ... ON CONFLICT DO UPDATE to keep the port’s overwrite behavior.
  • The schema omits a foreign key for orders.user_id because the domain accepts an order for an unknown user. An adapter must not introduce a new business rule.

The sample migration job creates tables with CREATE TABLE IF NOT EXISTS. It does not version schema changes or move records between databases. A real cutover needs a backfill, verification, a write strategy, and rollback steps.

05 · Agent-assisted change

Give agents a map, then test the boundary.

Clean names and small ports help an assistant locate the intended change. Kiro steering explains the dependency rule. Skills give repeatable tasks. An MCP server exposes architecture checks. In an IDE session, Kiro invokes the configured PreToolUse hook before an agent tool edit is applied. The hook can block an SDK import into the domain with AG001 and exit code 2.

PROPOSED SHORTCUT

domain/user.py imports boto3

The agent reaches from a business entity into the storage SDK. The hook rejects that proposed edit before it is written.

REPAIR PATH

Port → adapter → composition

State the operation the use case needs, implement it outside the core, inject it, then run the shared contract.

This improves change review and troubleshooting: a failing entity rule, contract test, adapter, and HTTP response have distinct owners. Teams can adopt it one action at a time: extract one action and one port before refactoring the whole app. No layout guarantees a correct agent answer; tests and review remain part of the loop.

The on-stage command replays a Kiro tool payload locally. Hook coverage depends on how edits are made. The separate git hook and CI template must be installed and enabled in a target repository; the architecture checker’s parse warnings call for a separate syntax or test gate.

06 · Claim discipline

Say exactly what the evidence supports.

SHOWN BY THE REPOCode portability

Core fingerprint and pod digest checks compare EKS, kind, and the local checkout when the stage command succeeds.

NEEDS A SEPARATE TESTRecovery

Define RTO/RPO; prove backups, restore or replication, and traffic switch under a failure drill.

SHOWN BY THE DEMO DESIGNSeparate data placement

Each target selects its own store. A write on one side is not implied to appear on the other.

NEEDS GOVERNANCE EVIDENCEData residency

Verify where data, backups, logs, telemetry, and access flows go. Document controls and permitted transfers.

kind runs on one laptop node. Its two PostgreSQL instances do not prove site-level recovery. Treat it as an on-premises stand-in that proves the application can run locally, subject to the tested dependencies and network setup.

07 · Present it

Make each screen answer one question.

For the 40-minute session, spend 10 minutes on the tax, core, and two axes. Use 25 minutes to trace one request, show the EKS/kind proof, flip Region persistence, replay the adapter addition, and reject the agent shortcut. Reserve five minutes for Q&A. Keep the two-target proof, adapter contract, and guard rejection if time runs short.

Ask a colleague to explain the two deployment diagram without your narration. If they say “automatic failover” or “compliant residency,” revise the line you used. The rehearsal succeeds when a listener can say what stayed fixed, what changed, and what is still unproved.
